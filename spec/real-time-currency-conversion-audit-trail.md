**Title:** Real-Time Currency Conversion & Audit Trail

**Business Idea:** Treasury operations teams at our enterprise customers
currently convert currency using manual lookups against a third-party
portal — slow, and it leaves no record for compliance. We need instant,
self-serve conversion inside our own app, and because these are regulated
transactions, every conversion must be reconstructable for an auditor on
demand, not pieced together afterward from emails or spreadsheets.

**Persona:** Treasury operations analysts at enterprise customers, who
process multiple cross-border settlements a day and are personally
accountable if a conversion can't be justified during an audit.

**User Need:** See a trustworthy converted amount the moment I enter it
— and be able to pull up any past conversion, with its rate and timestamp,
the moment an auditor asks for it.

**Known Constraints:**
- Frontend must read `VITE_API_URL` dynamically at container runtime using
  a generic entrypoint script placeholder replacement; replace the placeholder token
  `__VITE_API_URL__` inside the built `index.html` (or equivalent) with the runtime
  `VITE_API_URL` value.
- Backend must read database configurations exclusively from runtime
  environment variables.
- Backend must query external currency conversion data exclusively using a base URL from an environment variable (`CURRENCY_API_BASE_URL`), defaulting to an unauthenticated open-source endpoint like Frankfurter (`https://frankfurter.dev`).
- The application must not hardcode third-party API response schemas; utilize flexible JSON property mapping or an abstraction layer to isolate internal compliance tracking from external JSON structure changes (such as `rates` vs `conversion_rates`).
- The audit trail record must capture the exact execution timestamp generated by your backend server alongside any date or sequence markers returned by the external provider, ensuring complete sub-second audit reconstruction even if the provider only exposes a calendar date.
- External HTTP calls must handle failures gracefully with fallback values or clear domain exceptions rather than bubbling up raw network or serialization errors.
- CI/CD pipeline must inject placeholders safely at deployment time without
  exposing sensitive data in container layers.
- Restricted to specific stack versions: React (Vite/Node 24.*) and C#
  (**backend must target `net10.0` for build/test; CI must use `dotnet-version: 10.0.x`**).
- Must adhere to a strict folder layout (`src/frontend` and `src/backend`).
- A .NET solution file must always be generated at `src/backend/OuterloopLabApi.sln` via `dotnet new sln` + `dotnet sln add`, with the backend project added to it, and CI/build/test commands must invoke this `.sln` rather than the `.csproj` directly.
- Deploy as a single Azure Container App using the sidecar pattern to host
  both frontend and backend.
- Authenticate to Cosmos DB exclusively using token-based authentication via the pre-assigned User-Assigned Managed Identity, instantiated using `DefaultAzureCredential` configured with the specific `ManagedIdentityClientId`. Absolutely zero connection strings, master keys, or account keys are permitted in code, configurations, or logs.
- Utilize `Microsoft.Azure.Cosmos` and `Azure.Identity` packages for
  secure, token-based database interactions, including data-plane CRUD operations like adding and deleting items.
- Include `Azure.ResourceManager` and `Azure.ResourceManager.CosmosDB` packages to programmatically provision the Cosmos DB database and container via the control plane inside the application startup lifecycle (`Program.cs`) before the web application runs, utilizing the same token-based Managed Identity credentials for authentication.
  - ARM provisioning is best-effort; Managed Identity RBAC for ARM may differ from data-plane RBAC.
  - CRUD (and data-plane creation if needed) must be done via the Cosmos SDK (data-plane) using token-based Managed Identity credentials; access keys must not be used.
  - After ARM attempt, startup must run token-authenticated data-plane `CreateDatabaseIfNotExistsAsync` and `CreateContainerIfNotExistsAsync` and only proceed if the database/container are available (either already exist or were created). If token-authenticated data-plane create-if-not-exists fails, startup must fail.
- Map and bind all configuration values, including `AZURE_MANAGED_IDENTITY_CLIENT_ID`, endpoint URLs, and resource names, directly from the environment variables **using the exact keys** defined in `docs\CONTAINER_ENVIRONMENT_VARIABLES.md` without using local settings configuration files as fallbacks.

**Current Context:** Assumption: the implementation should be concentrated in `src/backend/Program.cs` for startup, configuration binding, Cosmos readiness checks, and HTTP endpoint wiring; `src/backend/OuterloopLabApi.sln` must remain the authoritative backend build/test entry; `src/frontend/index.html` must retain the `__VITE_API_URL__` placeholder for runtime replacement; and the existing React application entry/page files under `src/frontend/src/` (typically `src/frontend/src/main.jsx` or `src/frontend/src/main.tsx`) should host the currency conversion form, result display, and audit lookup screen.

**In Scope:**
- Add a backend conversion endpoint that accepts source currency, target currency, and amount, calls the configured external rate provider, and returns the converted amount together with a generated audit record identifier.
- Persist one Cosmos DB audit record for each successful conversion, including request inputs, normalized provider rate data, provider date or sequence markers if present, and the exact backend execution timestamp.
- Add a backend retrieval endpoint that returns a stored audit record by identifier without re-calling the external currency provider.
- Add frontend UI under `src/frontend/src/` for entering a conversion request, viewing the immediate result, and retrieving a prior conversion by audit record identifier.
- Render clear user-facing error states for upstream provider failures or invalid conversion requests.
- Add automated tests for successful conversion, audit record retrieval, and graceful upstream failure behavior.

**Out of Scope:**
- Historical exchange-rate lookup by arbitrary past date beyond what the upstream provider already returns for the live conversion request.
- Bulk or batch conversion workflows.
- Editing or deleting previously stored audit records.
- User authentication, authorization, or role management changes.
- Exporting audit records to PDF, CSV, email, or external compliance systems.
- Caching, scheduled rate synchronization, or offline conversion behavior beyond the single-request flow.

**Feature Constraints:**
- Use `IHttpClientFactory` for outbound currency-provider calls so timeout, base-address, and retry-related behavior stay centralized and testable.
- Introduce an internal provider-normalization layer so endpoint or UI-facing models never depend directly on upstream property names such as `rates` or `conversion_rates`.
- Use `decimal` for monetary values in backend request, persistence, and response models, and round the displayed converted amount to 2 decimal places using midpoint-away-from-zero financial rounding.
- Generate the audit record identifier in the backend and return it from the conversion response so the frontend can retrieve the exact persisted record later.
- Treat audit records as append-only documents for this feature; successful conversions create new records, and retrieval reads them back unchanged.
- When the upstream provider cannot supply a usable rate, return a stable domain response shape (preferably `ProblemDetails`) with a deterministic HTTP status code and without raw exception text.
- Keep frontend state local to the conversion/audit experience unless an existing application shell already requires a shared state container.

**Expected Outcome:** A treasury analyst can submit a request such as `amount=100.00`, `from=USD`, `to=EUR` and immediately receive a successful response that includes the converted amount, the applied exchange rate, a generated audit record identifier, the provider's effective date or sequence marker when available, and an `executedAtUtc` timestamp produced by the backend with sub-second precision. For example, if the normalized provider rate is `0.92`, the returned converted amount should be `92.00`, and a later audit lookup by the returned record identifier should reproduce the same `100.00 USD -> 92.00 EUR @ 0.92` result and timestamps from Cosmos DB without making another upstream HTTP call. If the upstream provider fails or returns unusable data, the conversion endpoint should return a clear `ProblemDetails` response with status `503` and a stable message that the frontend can render directly.

**Expected Agent Output:** OpenCode should produce backend changes under `src/backend` that add the conversion and audit retrieval API behavior, persistence models/services, and automated tests invoked through `src/backend/OuterloopLabApi.sln`; frontend changes under `src/frontend` that preserve runtime `VITE_API_URL` placeholder injection while adding the conversion and audit lookup UI; and verification steps showing the backend solution-based build/test path still works.

**Suggested Intent For OpenCode:** Create a plan and then implement this spec for real-time currency conversion plus audit retrieval, touching only the files required under `src/backend` and `src/frontend`. Respect every Known Constraint exactly as written, including the strict folder layout, runtime environment-variable binding, `src/backend/OuterloopLabApi.sln` build/test requirement, runtime `__VITE_API_URL__` placeholder replacement, token-authenticated Cosmos DB access and startup provisioning behavior, and the requirement to normalize upstream currency-provider JSON rather than hardcoding its schema. Ensure the backend returns a generated audit record identifier, persists append-only audit records with backend-generated execution timestamps, exposes retrieval by identifier, and returns a stable `ProblemDetails`-style `503` response when the upstream provider is unavailable.
